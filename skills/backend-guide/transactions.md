# Транзакции, несколько доменов, события

## Единица работы

- Одна единица работы (UoW) на запрос / апдейт / сообщение брокера.
  Её сессию получают все Gateway запроса, в том числе соседей.
- Соединение берётся при первом обращении и возвращается в пул сразу после
  `commit()`/`rollback()`. Gateway не запоминает соединение — каждый раз
  просит его у UoW.
- Без `commit()` и при исключении — откат (выход из области REQUEST).

## Порядок «база ↔ внешний мир» (TX-02, TX-03)

Спроси: «что будет, если процесс упадёт между шагами?» Выбирай порядок,
после которого состояние исправимо повтором.

| Задача | Порядок |
|---|---|
| Ссылка для входа по почте | сохранить ссылку → commit → отправить письмо |
| Уведомить после записи | записать → commit → отправить (или outbox) |
| Списать во внешней системе, потом записать | идемпотентный ключ во внешнем вызове → вызов → запись; повтор безопасен |
| Создать во внешней системе, ответ нужен в записи | внешний вызов → запись; при сбое записи — сверка/дожим |

## Сценарий на несколько доменов (APP-04, TX-04)

```
OrderFulfillmentService.fulfill(order_id)
  1. claim = orders_gateway.claim(order_id)         # свой Gateway
  2. plan  = orders_gateway.plan(claim)             # неизменяемый план, без строк БД
  3. subscriptions.credit(plan.credit)              # порт соседа: пишет в ЭТОЙ транзакции, не коммитит
  4. referrals.reward(plan.reward)                  # порт соседа
  5. orders_gateway.mark_applied(order_id)          # отметка — в той же транзакции (TX-10)
  6. transaction.commit()
  7. после коммита: уведомления, внешние вызовы
```

- На каждого участника — свой порт в `application/interfaces/` домена-инициатора.
- Сосед реализует его в `public.py` протоколом `{Сосед}{Что}Transfer` без
  коммита. Если протокол соседа уже подходит, провайдер отдаёт его как есть:
  `def credit(self, t: SubscriptionsCreditTransfer) -> SubscriptionCredit`.
- Порядок шагов держит внешние ключи (родитель до детей, удаление последним)
  и записан в docstring сервиса.

**Нужен шаг соседа посередине сценария** (APP-05): сценарий делится на фазы,
контроллер вызывает соседа между ними:

```python
access = await subscriptions.check(token)            # фаза 1
link = await accounts.cabinet_link(access.user_id)   # сосед
result = await subscriptions.sync(access, link)      # фаза 2
```

## Конфликт уникальности (TX-07)

```python
async def set_email(self, user_id: int, email: str) -> None:
    try:
        async with self._session.begin_nested():     # savepoint
            await self._session.execute(update(...))
    except IntegrityError as exc:
        raise EmailBusyError(email) from exc         # транзакция запроса жива
```

## Блокировки (TX-08)

- Общая блокировка записи (advisory lock / `FOR UPDATE` строки-владельца) —
  первым шагом, до чтения строк.
- Порядок блокировок нескольких ресурсов — одинаковый во всех путях.
- Функция, которую зовут уже под блокировкой, сама её не берёт.

## События

**Внутри процесса** (тот же сервис, та же база): агрегат копит события;
после успешного коммита единица работы передаёт их обработчикам. Потеря
при падении процесса возможна — если это недопустимо, используй outbox.

**Наружу** (брокер, другой сервис) — outbox (TX-09):

```
транзакция:  изменить агрегат + INSERT INTO outbox(id, type, payload, created_at)
             commit
relay:       SELECT … FROM outbox WHERE published_at IS NULL ORDER BY id FOR UPDATE SKIP LOCKED
             publish → UPDATE outbox SET published_at = now()
```

- Сообщение несёт id события; потребитель хранит обработанные id
  (inbox / уникальный ключ) — доставка at-least-once (TX-10).
- Сценарий не вызывает `publish()` сам.

## Вебхуки и повторы (TX-10)

- Проверять «уже исполнено», а не «уже получено/оплачено».
- Неидемпотентный шаг и его отметка — в одной транзакции.
- Захват в работу (`claimed_at`) — с протуханием (минуты), снимается сразу
  при неудаче.
- Фоновый дожим: получено, но не исполнено дольше N минут.
- Однократный бэкфилл — с засечкой (DB-04), иначе дожим примет историю за
  неисполненное.
