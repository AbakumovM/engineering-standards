# Каталог правил бэкенд-сервиса

Группы: STR, DEP, DOM, APP, TX, CTL, ADP, DI, DB — архитектура; API, SEC,
PERF, REL, OBS, OPS — поведение сервиса под нагрузкой, при сбоях и атаках;
TST, LEG, TYP, NAM — тесты, перенос, типы, имена.

Единый источник правил. Руководство (`backend-guide`), ревью
(`backend-review`) и проекты ссылаются на правила по номеру.

## Как читать

Каждое правило:

- **Уровень.** `обязательно` — принцип, нарушение = дефект. `по умолчанию` —
  разумный выбор; проект может отступить, записав отклонение (см. ниже).
- **Почему** — что ломается без правила.
- **Проверка.** `авто` — команда или поиск, которые находят нарушение
  без модели; `вручную` — на что смотреть при ревью.
- **Исключение** — когда отступить допустимо и как это оформить.

## Отклонения в проекте

Проект записывает отступления в своём `AGENTS.md` / `CLAUDE.md` в разделе
«Отклонения от общих правил», по одной строке:

```
- TX-02: исключение в devices — внешний вызов под FOR UPDATE, чтобы из
  одновременных изменений прошло ровно одно. Новых таких мест не заводить.
- DB-01: asyncpg и чистый SQL вместо SQLAlchemy.
```

Записанное отклонение — не нарушение. Незаписанное — нарушение.

## STR — структура

### STR-01. Сначала домены, внутри — слои
**Уровень:** обязательно.
Верхний уровень `src/<пакет>/` — домены (`orders/`, `accounts/`), внутри
каждого — слои. Не наоборот (`models/`, `services/`, `routers/` поверх всех доменов).
**Почему:** деление по типам файлов перестаёт работать уже на нескольких
доменах: одна фича размазана по всему дереву, границ нет.
**Проверка:** вручную — в корне пакета только домены, `infrastructure/` и точки сборки.

### STR-02. Одинаковые слои у всех доменов
**Уровень:** по умолчанию.
Каждый домен: `domain/`, `application/`, `adapters/`, `controllers/`, `ioc.py`,
`public.py`. У маленького домена слой может быть тонким (один файл), но он есть.
**Почему:** единообразие дешевле, чем выбор раскладки на каждый домен;
контракты границ пишутся одним шаблоном.
**Проверка:** авто — у каждого домена есть все слои (`backend-review/scripts/arch_check.py`).

### STR-03. Файл появляется вместе с содержимым
**Уровень:** обязательно.
Не заводить заранее пустые `commands.py`, `events.py`, `services/`, `v1/`.
Слой существует всегда (STR-02), файлы внутри — по необходимости.
**Почему:** пустые заготовки создают видимость структуры и путают, где что лежит.
**Проверка:** авто — пустые модули (только docstring/`pass`).

### STR-04. Нет `common/`, `utils/`, `helpers/` как свалки
**Уровень:** обязательно.
Общая техника — в `infrastructure/<назначение>/` (`db/`, `http/`, `mail/`).
Общее правило — в домене-владельце, соседи берут его через `public.py`.
**Почему:** свалка становится модулем, от которого зависят все и который
нельзя изменить.
**Проверка:** авто — каталоги с такими именами.

### STR-05. Сборка — только в точках входа
**Уровень:** обязательно.
Контейнер DI, порядок роутеров, запуск фоновых задач — в точке сборки
(`main.py`, `app.py`, `<процесс>_main.py`). Домены не собирают себя сами
и не знают, в какой процесс включены.
**Почему:** одни и те же домены подключаются к HTTP, боту, воркеру, CLI.
**Проверка:** вручную.

### STR-06. Модульный монолит по умолчанию
**Уровень:** по умолчанию.
Один репозиторий, один деплой, домены вызывают друг друга в процессе.
Отдельный сервис — только по проверенной границе (своя нагрузка, своя
команда, своя база) и после того, как граница прожила в монолите.
**Почему:** сетевой вызов между своими модулями — лишняя точка отказа
и потеря транзакции.
**Проверка:** вручную.

## DEP — зависимости и границы

### DEP-01. Зависимости направлены внутрь
**Уровень:** обязательно.
`domain` ← `application` ← `adapters`, `controllers`. Внутренний слой не
импортирует внешний.
**Проверка:** авто — контракт `layers` в import-linter.

### DEP-02. `domain` ни от чего не зависит
**Уровень:** обязательно.
В `domain/` нет импортов фреймворков (FastAPI, aiogram, FastStream), ORM и
драйверов БД, httpx, pydantic, настроек, других доменов и `infrastructure`.
Только стандартная библиотека и сам домен.
**Почему:** правило проверяется модульным тестом за миллисекунды и
переживает смену фреймворка.
**Проверка:** авто — контракт `forbidden` для `*.domain`.
**Исключение:** нет.

### DEP-03. `application` не импортирует `infrastructure` и адаптеры
**Уровень:** обязательно.
Сценарий получает зависимости портами (`Protocol` в `application/interfaces/`),
настройки — значением (`{Что}Config` в `application/config.py`, его собирает
провайдер из `Settings`).
**Проверка:** авто — контракт `forbidden`.

### DEP-04. Сосед — только через `public.py`
**Уровень:** обязательно.
Другие домены импортируют только `<домен>.public`: протоколы View, `Info`,
порты записи для чужой транзакции (TX-04). Внутренности домена закрыты.
**Почему:** без этого через полгода «модули» снова одна каша, разложенная по папкам.
**Проверка:** авто — контракт `protected` / `independence` на домен.

### DEP-05. Таблица принадлежит одному домену
**Уровень:** обязательно.
Читает и пишет таблицу только её домен. Сосед получает данные через
`public.py`, на чужие сущности ссылается по id, не по объекту.
**Почему:** таблица с двумя писателями — правило, размазанное по двум местам.
**Проверка:** вручную — имена чужих таблиц в SQL/моделях домена; авто — поиск
по списку таблиц домена, если он ведётся.
**Исключение:** массовый SQL, которому нужно правило соседа, получает от
соседа готовый построитель условия через `public.py` (DOM-04).

### DEP-06. Границы проверяются в CI
**Уровень:** обязательно.
import-linter (или Tach) в CI и перед push. Известное нарушение — в
`ignore_imports` с комментарием «зачем и когда снимется». Число
исключений — технический долг, оно должно только уменьшаться.
**Почему:** правило без проверки перестаёт соблюдаться.
**Проверка:** авто — `lint-imports`; каждый новый контракт проверить пробным нарушением.

### DEP-07. Нужен вызов «вверх» — инверсия через порт
**Уровень:** обязательно.
Если нижнему слою или домену нужно поведение верхнего, он объявляет порт,
верхний его реализует.
**Проверка:** авто — DEP-01, DEP-04.

## DOM — домен

### DOM-01. Правило — чистая функция в `domain/`
**Уровень:** обязательно.
Решение («сколько стоит», «когда истекает», «можно ли») — функция или метод
над простыми значениями в `domain/`, без I/O. Деньги, сроки и доступ —
обязательно с модульными тестами.
**Почему:** правило в контроллере или SQL дублируется при втором входе
(бот + сайт + админка) и не тестируется без инфраструктуры.
**Проверка:** вручную — условия про деньги/сроки/доступ вне `domain/`.

### DOM-02. «Можно ли» возвращает причину отказа
**Уровень:** по умолчанию.
Проверка возвращает значение-причину (`enum`/dataclass), а не `bool`.
Контроллер решает только, как показать причину.
**Почему:** разным входам нужен разный текст, а правило одно.
**Проверка:** вручную.

### DOM-03. Доменные исключения
**Уровень:** обязательно.
`domain/exceptions.py`: `{Что}NotFoundError`, `{Что}BusyError` и т.п.
Адаптеры и сценарии бросают их, а не `ValueError`/`KeyError`/исключения драйвера.
**Проверка:** авто — `raise ValueError`/`raise Exception` в `application/`, `adapters/`.

### DOM-04. Правило соседа не копируется
**Уровень:** обязательно.
Нужно чужое правило — его результат приходит готовым полем `Info` или
функцией через `public.py` соседа.
**Проверка:** вручную — похожие условия в двух доменах.

### DOM-05. Правило сверки с внешней системой — в домене
**Уровень:** по умолчанию.
Что считать расхождением с внешним сервисом, решает функция домена; клиент
сервиса только читает и пишет.
**Почему:** правило тестируется без сервиса, разные сценарии применяют его по-своему.
**Проверка:** вручную — сравнения и допуски внутри клиента/адаптера.

### DOM-06. Доменные события — прошедшим временем, внутри агрегата
**Уровень:** по умолчанию.
`AssetCreated`, `OrderPaid`. Агрегат добавляет событие в свой список; наружу
событие уходит по TX-09.
**Проверка:** вручную.

## APP — сценарии

### APP-01. Interactor: один агрегат, один Gateway
**Уровень:** обязательно.
`{Entity}Interactor` меняет один агрегат через свой `{Entity}Gateway`.
Кроме Gateway может получать порты внешних сервисов, `Transaction` и
порты чтения соседей.
**Почему:** сценарий, пишущий несколько агрегатов, — скрытый сервис без
явного места для порядка шагов и отката.
**Проверка:** вручную — два и более Gateway записи в конструкторе.

### APP-02. Сценарий возвращает неизменяемый `Info`
**Уровень:** обязательно.
`{Entity}Info` — `@dataclass(frozen=True, slots=True)` в `application/dto.py`.
Не доменная модель, не строка ORM, не pydantic-схема ответа.
**Почему:** вызывающий не может изменить состояние в обход сценария.
**Проверка:** авто — возвращаемые типы публичных методов Interactor.

### APP-03. Чтение для ответа — View, чтение для решения — Gateway
**Уровень:** обязательно.
- `{Entity}View` (чтение) — в контроллерах и сервисах, для ответа пользователю.
- Данные, на основании которых сценарий решает и пишет, читает Gateway
  своего домена (в транзакции, с блокировкой при необходимости).
- Своего View в Interactor нет. Порт чтения соседа (`application/interfaces/`)
  допустим.
**Почему:** решение по данным, прочитанным вне транзакции, — гонка.
**Проверка:** вручную — View своего домена в конструкторе Interactor.

### APP-04. Сервис — когда одна транзакция пишет несколько доменов
**Уровень:** по умолчанию.
`{Workflow}Service` в `application/<сценарий>.py` домена-инициатора, когда:
- одна транзакция должна записать данные нескольких доменов, или
- один и тот же процесс из 3+ шагов вызывается из нескольких входов
  (HTTP, бот, очередь, CLI).
Порядок шагов (внешние ключи: родитель до детей, удаление последним) —
в docstring сервиса. Сервис не видит строк БД: Gateway сводит данные в
неизменяемый план (`{Что}Plan`), сервис передаёт его дальше.
**Исключение:** между независимыми модулями (своя база, отдельный процесс) —
не общая транзакция, а события (TX-09).
**Проверка:** вручную.

### APP-05. Сценарий не вызывает сценарий другого домена
**Уровень:** обязательно.
Оркестрирует контроллер (1–2 шага) или сервис (APP-04). Если чужой шаг
нужен посередине — сценарий делится на фазы (`check` → сосед → `apply`),
между ними вызывает контроллер.
**Проверка:** вручную — Interactor соседа в конструкторе Interactor.

### APP-06. Внешний сервис — порт домена
**Уровень:** обязательно.
Письмо, СМС, платёжка, внешнее API: `Protocol` в
`application/interfaces/<сервис>.py`, реализация в `adapters/<сервис>.py`.
**Проверка:** авто — импорт клиентов (httpx, SDK) вне `adapters/` и `infrastructure/`.

### APP-07. Не делать сервис «на вырост»
**Уровень:** по умолчанию.
1–2 сценария в одном входе — оркестрация в контроллере. Сервис появляется,
когда выполнено условие APP-04.
**Проверка:** вручную — сервис, который вызывает один Interactor.

## TX — транзакции и согласованность

### TX-01. Коммит явный, в сценарии
**Уровень:** по умолчанию.
Сценарий заканчивает метод `await transaction.commit()`. Исход без записи
(«почта занята») — `rollback()`. Исключение — откат. `Transaction` — порт
домена, реализует его единица работы запроса.
**Почему:** видно, где граница транзакции; транзакция не висит открытой,
пока контроллер ходит во внешние сервисы.
**Проверка:** авто — `commit()` в `controllers/`, `adapters/`; вручную —
путь метода без commit/rollback.

### TX-02. Внутри транзакции нет внешних вызовов
**Уровень:** обязательно.
Пока открыта транзакция, не ходить в HTTP, очереди, почту, мессенджеры.
Внешний вызов — до сценария или после коммита.
**Почему:** соединение пула занято всё время ожидания; медленный внешний
сервис исчерпывает пул и кладёт весь сервис.
**Проверка:** вручную — вызов порта внешнего сервиса между первым
обращением к Gateway и commit.
**Исключение:** когда внешний вызов должен быть атомарен с блокировкой
строки и вызовы редкие — записать в проекте с причиной.

### TX-03. Порядок «запись ↔ внешний вызов» — от безопасного сбоя
**Уровень:** обязательно.
Выбрать порядок так, чтобы сбой между шагами оставлял исправимое
состояние. Обычно: сначала сохранить и закоммитить, потом отправить
(ссылка есть в базе, письмо не ушло → пользователь запросит ещё раз).
Наоборот — письмо со ссылкой, которой нет.
**Проверка:** вручную.

### TX-04. Фиксирует владелец транзакции
**Уровень:** обязательно.
Сервис на несколько доменов коммитит и откатывает сам. Порт соседа для
чужой транзакции (`{Сосед}Transfer`, через `public.py`) работает в
транзакции вызывающего и `commit()` не вызывает. Сценарий соседа с
коммитом внутрь чужой транзакции не встраивать.
**Проверка:** вручную.

### TX-05. View читает вне единицы работы
**Уровень:** по умолчанию.
View берёт своё соединение/сессию и сразу отпускает. Свои незакоммиченные
записи View не видит — если они нужны, это метод Gateway.
**Проверка:** вручную.

### TX-06. Нет параллельных запросов на одном соединении
**Уровень:** обязательно.
`asyncio.gather` по одной сессии/соединению запрещён (asyncpg и
AsyncSession этого не поддерживают).
**Проверка:** вручную — `gather` в сценариях и Gateway.

### TX-07. Ожидаемый конфликт — точка сохранения
**Уровень:** обязательно.
Если нарушение уникальности — нормальный исход («почта занята»), запись
идёт во вложенной транзакции (savepoint), ошибка БД переводится в
доменное исключение. Иначе ошибка ломает всю транзакцию запроса.
**Проверка:** вручную — перехват `IntegrityError`/`UniqueViolationError` без savepoint.

### TX-08. Единый порядок блокировок
**Уровень:** обязательно.
Если запись таблицы сериализуется общей блокировкой (advisory lock,
`FOR UPDATE` строки-владельца), все пути берут её первым шагом, до чтения
строк. Порядок блокировок нескольких ресурсов — одинаковый везде.
**Почему:** обратный порядок — взаимная блокировка.
**Проверка:** вручную.

### TX-09. События наружу — через outbox
**Уровень:** по умолчанию.
Событие для других процессов (брокер, другой сервис) пишется в таблицу
outbox **в той же транзакции**, что и изменение; отдельный процесс
публикует и отмечает. Публикация «после коммита» из памяти теряет
событие при падении процесса.
Внутрипроцессные события (тот же процесс, та же база) могут обрабатываться
после коммита без outbox, если потеря допустима — записать это.
**Проверка:** вручную — `publish()` в сценарии или после commit без outbox.

### TX-10. Обработчики входящих событий и вебхуков идемпотентны
**Уровень:** обязательно.
Доставка повторяется (ретраи провайдера, at-least-once брокера). Обработчик
проверяет «уже исполнено», а не «уже получено». Неидемпотентный шаг
(начисление) и отметка о нём — в одной транзакции. Захват в работу — с
протуханием, чтобы упавший процесс не заклинил запись. Должен быть
фоновый дожим того, что получено, но не исполнено.
**Проверка:** вручную.

## CTL — контроллеры

### CTL-01. Разобрать → вызвать → ответить
**Уровень:** обязательно.
Контроллер разбирает вход, вызывает сценарии/View, формирует ответ. Ни
одного `if` про деньги, сроки, доступ, статусы. Сущности не создаёт.
**Проверка:** вручную; авто-эвристика — арифметика с датами/суммами,
обращения к Gateway и `commit()` в `controllers/`.

### CTL-02. Представление живёт в контроллере
**Уровень:** по умолчанию.
Тексты, клавиатуры, шаблоны, схемы запроса/ответа — `controllers/`.
Тексты, которые зависят от правила (условия акции), — функцией в `domain/`.
**Проверка:** вручную.

### CTL-03. Доступ — фильтром или зависимостью
**Уровень:** по умолчанию.
Проверка прав — фильтр роутера / `Depends`, не `return` в начале тела.
**Почему:** в роутерах с цепочкой обработчиков ранний `return` всё равно
«съедает» событие.
**Проверка:** вручную.

### CTL-04. Доменные исключения → ответы в одном месте
**Уровень:** по умолчанию.
Перевод исключений в HTTP-коды/сообщения — обработчиком исключений или
единым помощником, а не `try/except` в каждом маршруте.
**Проверка:** вручную.

## ADP — адаптеры и инфраструктура

### ADP-01. Внешний клиент — один на процесс, с таймаутами
**Уровень:** обязательно.
HTTP-клиенты, пулы, SDK создаются один раз в `infrastructure/` и
передаются через DI. У каждого — таймауты соединения и запроса.
**Почему:** клиент на каждый запрос — утечка соединений; без таймаута
обрыв сети = «висим вечно».
**Проверка:** авто — `httpx.AsyncClient(`/`ClientSession(` вне `infrastructure/`;
создание пула без `timeout`.

### ADP-02. Ошибки внешнего API — одним исключением порта
**Уровень:** по умолчанию.
Адаптер переводит сетевые и протокольные ошибки в одно исключение
(`{Сервис}Error`). Сценарий не знает про httpx.
**Проверка:** вручную.

### ADP-03. Синхронный SDK — не в event loop
**Уровень:** обязательно.
Блокирующий вызов — через `asyncio.to_thread`/threadpool. CPU-тяжёлое —
в отдельный процесс/воркер.
**Проверка:** авто — `requests`, `time.sleep`, синхронные драйверы в async-коде.

### ADP-04. Данные формирует БД
**Уровень:** по умолчанию.
Соединения, агрегаты, фильтрация, пагинация — в SQL, не циклом в Python.
**Проверка:** вручную — выборка всего и фильтр в Python, N+1.

### ADP-05. Перенесено в REL-04 (health-проверки)

## DI — сборка зависимостей

### DI-01. Провайдеры по слоям домена
**Уровень:** по умолчанию.
`ioc.py` домена: `{Домен}AdaptersProvider` (Gateway, View, порты),
`{Домен}InteractorsProvider` (сценарии, их Config); функция

**Проверка:** вручную.

### DI-02. Адаптер под протокол — функцией с типом результата
**Уровень:** обязательно (Dishka).
```python
@provide(scope=Scope.APP)
def view(self, pool: Pool) -> AccountView:
    return PgAccountView(pool)
```
а не `provide(PgAccountView, provides=AccountView)`: так mypy сверяет

**Проверка:** авто — `provides=` в `ioc.py`.

### DI-03. Области жизни
**Уровень:** по умолчанию.
Без состояния (View на пуле, клиенты, Config) — `APP`. Единица работы,
Gateway, сценарии — `REQUEST`.
**Проверка:** вручную.

### DI-04. Нет глобального состояния
**Уровень:** обязательно.
Никаких модульных синглтонов клиентов/сессий и `global`. Всё через контейнер.
**Проверка:** авто — `global`, создание клиентов на уровне модуля.

## DB — данные и миграции

### DB-01. Доступ к БД — только через Gateway/View
**Уровень:** обязательно.
ORM/драйвер — внутри `adapters/`. Выбор по умолчанию — SQLAlchemy (async)
+ Alembic; asyncpg и чистый SQL — допустимое отклонение.
**Проверка:** авто — импорт `sqlalchemy`/`asyncpg` вне `adapters/`, `infrastructure/`, `migrations/`.

### DB-02. Схему создают только миграции
**Уровень:** обязательно.
Ни одного `CREATE`/`ALTER` в коде приложения. Миграция статична (не
импортирует модели приложения), с понятным именем; необратимая — помечена.
**Проверка:** авто — DDL в `src/`; импорт приложения в `migrations/`.

### DB-03. Именование ограничений и индексов задано
**Уровень:** по умолчанию.
`naming_convention` в метаданных (`ix_`, `uq_`, `fk_`, `pk_`, `ck_`):
иначе автогенерация даёт случайные имена и миграции не переносимы.
**Проверка:** вручную.

### DB-04. Одноразовые засечки — явно
**Уровень:** по умолчанию.
Однократные операции над данными (бэкфилл) отмечаются записью-засечкой,
чтобы повторный запуск не повторил их.
**Проверка:** вручную.

## API — контракт HTTP API

Подробности и примеры — `api.md`.

### API-01. Явные схемы входа и выхода
**Уровень:** обязательно.
Тело запроса и ответа — свои схемы (pydantic) в `controllers/`, отдельно от
`Info`, доменных моделей и строк ORM. Ответ содержит только перечисленные
поля. Схема команды не принимает лишних полей (`extra="forbid"`) и не
содержит полей, которые клиент менять не вправе (`id`, `role`, `balance`).
**Почему:** OWASP API3 — утечка лишних полей и mass assignment
(клиент прислал `is_admin: true`, и оно записалось).
**Проверка:** вручную — маршрут возвращает `Info`/модель напрямую, схема
ответа «как есть» из ORM, `**body.model_dump()` в сущность.

### API-02. Единый формат ошибок
**Уровень:** обязательно.
Все ошибки — одного формата: RFC 9457 (`application/problem+json`: `type`,
`title`, `status`, `detail`, плюс `request_id`) или свой, но один на сервис.
Обработчики исключений зарегистрированы для доменных ошибок, ошибок валидации
и необработанного `Exception`. В ответе нет стектрейсов, SQL, внутренних путей.
**Проверка:** вручную — маршруты с собственным форматом ошибок, `detail=str(exc)`.

### API-03. Коды ответа по смыслу
**Уровень:** по умолчанию.
`400` — запрос не разобрать; `401` — не аутентифицирован; `403` — нет прав;
`404` — нет объекта **или нет прав его видеть** (не раскрывать существование);
`409` — конфликт состояния; `422` — данные корректны по форме, но нарушают
правило; `429` — лимит; `503` — зависимость недоступна, можно повторить.
`5xx` — только ошибка сервера, никогда не ответ на плохие данные.
**Проверка:** вручную.

### API-04. Пагинация у любого списка — с первого дня
**Уровень:** обязательно.
Эндпоинт списка принимает `limit` с потолком (например, ≤100) и курсор или
страницу; ответа «всё сразу» нет. Для растущих таблиц — keyset (курсор по
`(created_at, id)`), не `OFFSET`. Курсор непрозрачен, не даёт доступа
(права проверяются на каждом запросе), остальные параметры запроса с ним
не меняются. Сортировка детерминирована (уникальный хвост — `id`).
**Почему:** добавить пагинацию потом — ломающее изменение (Google AIP-158);
`OFFSET` на большой таблице — полный проход.
**Проверка:** авто — маршрут возвращает `list[...]` без параметра `limit`/`cursor`.

### API-05. Идемпотентность операций с последствиями
**Уровень:** обязательно.
`POST`, который создаёт, списывает или отправляет, принимает заголовок
`Idempotency-Key`. Сервер хранит ключ, отпечаток тела и ответ (срок — часы/сутки),
повтор с тем же ключом возвращает сохранённый ответ; тот же ключ с другим
телом — `422`; ключ обязателен, но не передан — `400`. `PUT`/`DELETE`
идемпотентны по смыслу.
**Почему:** клиент повторяет запрос после таймаута — без ключа второй платёж.
**Проверка:** вручную — создающие/платёжные `POST` без ключа.

### API-06. Обратная совместимость
**Уровень:** обязательно.
Можно: добавить необязательное поле запроса, поле ответа, новый эндпоинт,
новое значение там, где клиенты к этому готовы. Нельзя без новой версии:
удалить или переименовать поле, сменить тип или формат, сделать поле
обязательным, изменить смысл кода ответа. Версия (`/v2`) — только при ломке.
Клиенты сервиса игнорируют неизвестные поля.
**Проверка:** вручную — дифф схем ответа.

### API-07. Ограничения входа
**Уровень:** обязательно.
У каждого входа есть потолок: размер тела, длина строк (`max_length`),
размер массивов, диапазоны чисел, размер и тип загружаемых файлов.
**Почему:** OWASP API4 — неограниченное потребление ресурсов одним запросом.
**Проверка:** вручную — `str`/`list` в схеме запроса без ограничений.

### API-08. Опись API
**Уровень:** по умолчанию.
OpenAPI генерируется из кода и описывает ошибки; в проде документация
закрыта или за авторизацией. Неиспользуемые и старые версии эндпоинтов
удаляются, а не остаются «на всякий случай» (OWASP API9).
**Проверка:** вручную.

### API-09. Время, деньги, идентификаторы в контракте
**Уровень:** обязательно.
Время — ISO 8601 с зоной (`2026-11-23T10:00:00Z`). Деньги — целое в минорных
единицах или строка-десятичное плюс код валюты, не `float`. Публичный id —
непрозрачный (UUID/ULID), если последовательные id раскрывают объёмы или
упрощают перебор.
**Проверка:** вручную; авто — OPS-01, OPS-02.

## SEC — безопасность

Подробности — `security.md`. Основа — OWASP API Security Top 10 (2023).

### SEC-01. Доступ к объекту проверяется в сценарии
**Уровень:** обязательно.
Каждый сценарий, получающий id объекта, проверяет право субъекта на этот
объект: правило доступа — в `domain/` (DOM-01), запрос к БД фильтрует по
владельцу/арендатору (`WHERE id = :id AND owner_id = :subject`). Контроллер
передаёт субъекта, но решение не принимает. Нет прав — `404` (API-03).
**Почему:** OWASP API1 (BOLA) — самая частая уязвимость API: поменял id в
URL — получил чужое.
**Проверка:** вручную — метод Gateway/View «по id» без субъекта; сценарий
без параметра субъекта.

### SEC-02. Доступ к функции — запрещено, пока не разрешено
**Уровень:** обязательно.
Админские и служебные маршруты — отдельным роутером с зависимостью роли на
весь роутер; новый маршрут без явной политики доступа недоступен. Внутренние
API — отдельный ключ/сеть, не «секретный URL».
**Почему:** OWASP API5 (BFLA).
**Проверка:** вручную — админский маршрут в общем роутере, проверка роли в теле.

### SEC-03. Аутентификация
**Уровень:** обязательно.
Пароли — argon2id (или bcrypt), никогда быстрый хеш. Сравнение токенов и
подписей — `hmac.compare_digest`. У токенов и сессий есть срок; выход и смена
пароля отзывают сессии. Лимит попыток входа и восстановления (SEC-09/REL).
Ответ входа не различает «нет пользователя» и «неверный пароль».
**Проверка:** авто — `==` при сравнении подписи/токена (эвристика), `md5`/`sha1`
рядом со словом password; вручную — остальное.

### SEC-04. Секреты
**Уровень:** обязательно.
Секреты — только из окружения или хранилища секретов, типом `SecretStr`;
не в коде, не в репозитории (`.env` в `.gitignore`), не в логах, не в
ответах, не в сообщениях об ошибках. У секрета нет значения по умолчанию.
**Проверка:** авто — строковые константы в переменных `*password*`, `*secret*`,
`*token*`, `*api_key*`.

### SEC-05. Только параметризованный SQL
**Уровень:** обязательно.
Значения — параметрами. Динамические имена колонок/сортировки — из белого
списка, не из ввода.
**Проверка:** авто — f-строка, `%`, `+`, `.format()` в аргументе `execute`/`fetch*`/`text()`
(и ruff `S608`).

### SEC-06. Вебхуки
**Уровень:** обязательно.
Подпись проверяется по сырому телу запроса, `hmac.compare_digest`; защита от
повтора — окно времени по метке и уникальный id события (TX-10). Без
подписи — список адресов отправителя плюс сверка статуса у провайдера по API.
**Проверка:** вручную.

### SEC-07. Исходящие запросы по адресу из ввода (SSRF)
**Уровень:** обязательно.
Если сервис ходит по URL, пришедшему извне (вебхук клиента, загрузка по
ссылке): белый список схем и хостов, запрет приватных и служебных адресов
после разрешения DNS, без автоматических редиректов, таймаут и потолок размера.
**Почему:** OWASP API7.
**Проверка:** вручную — `client.get(url)` с url из запроса.

### SEC-08. Ответы чужих API — недоверенный ввод
**Уровень:** обязательно.
Ответ внешнего сервиса разбирается схемой (поля, типы, размер), а не
`response.json()["a"]["b"]` в сценарии; таймаут и потолок размера ответа.
**Почему:** OWASP API10 — небезопасное потребление API.
**Проверка:** вручную — словари внешнего ответа за пределами адаптера.

### SEC-09. Защита бизнес-процессов от автоматизации
**Уровень:** по умолчанию.
Регистрация, вход, восстановление, промокоды, оплата, отправка писем/СМС —
лимит частоты на пользователя/IP/объект и, где нужно, подтверждение
(капча, код). Лимит — в общем месте (middleware/зависимость), ответ `429`
с `Retry-After`.
**Почему:** OWASP API6 и API4.
**Проверка:** вручную.

### SEC-10. Настройки безопасности HTTP
**Уровень:** обязательно.
CORS — явный список origin (не `*` вместе с credentials). Cookie сессии —
`Secure`, `HttpOnly`, `SameSite`. Отладочный режим и подробные ошибки в
проде выключены.
**Проверка:** авто — `allow_origins=["*"]`, `debug=True`; вручную — cookie.

### SEC-11. Зависимости
**Уровень:** обязательно.
Lock-файл в репозитории (`uv.lock`); проверка уязвимостей зависимостей в CI
(`pip-audit` или аналог); обновления — регулярно, а не при пожаре.
**Проверка:** вручную — наличие шага в CI.

## PERF — нагрузка

Подробности — `performance.md`.

### PERF-01. Нет N+1
**Уровень:** обязательно.
Связанные данные — одним запросом (JOIN, `IN (...)`, `selectinload`), а не
запросом в цикле. Каждый запрос в цикле — подозрение.
**Проверка:** авто — `await` вызова Gateway/View/`session`/`conn` внутри `for` (эвристика).

### PERF-02. Запрос по растущей таблице — с индексом
**Уровень:** обязательно.
Новый запрос с фильтром/сортировкой по таблице, которая растёт, имеет
индекс под фильтр и сортировку. Тяжёлый запрос проверен `EXPLAIN (ANALYZE)`
на реалистичном объёме данных. Индекс — в миграции (OPS-04).
**Проверка:** вручную.

### PERF-03. Бюджет соединений БД
**Уровень:** обязательно.
`экземпляры × процессы × (pool_size + max_overflow) + фоновые задачи + миграции
≤ max_connections − резерв администратора`. Число записывается в
`AGENTS.md` проекта. Много экземпляров — PgBouncer в режиме transaction.
**Почему:** лишний воркер или экземпляр незаметно исчерпывает соединения, и
падает всё сразу.
**Проверка:** вручную.

### PERF-04. Таймауты в БД
**Уровень:** обязательно.
Для роли приложения: `statement_timeout` (интерактивные запросы падают
быстро), `idle_in_transaction_session_timeout` (забытая транзакция не держит
блокировки и не мешает VACUUM). Тяжёлый отчёт — свой таймаут явно, а не
повышение общего. Миграции — `lock_timeout` (OPS-04).
**Проверка:** вручную — настройки пула/роли.

### PERF-05. Ограниченная параллельность и обратное давление
**Уровень:** обязательно.
Параллельные вызовы внешнего API и тяжёлые операции ограничены семафором /
лимитом; внутренние очереди — с потолком. При переполнении — быстрый отказ
(`429`/`503`), а не бесконечное ожидание. `asyncio.gather` по неограниченному
списку запрещён.
**Проверка:** авто — `gather(*[...])` по генератору/списку без семафора (эвристика).

### PERF-06. Долгая работа — не в запросе
**Уровень:** обязательно.
Работа дольше нескольких секунд или с повторами — в очередь/фоновую задачу
со статусом, запрос отвечает сразу (`202` + id задачи). `BackgroundTasks` —
только для неважного: задача теряется при перезапуске.
**Проверка:** авто — использование `BackgroundTasks` (предупреждение).

### PERF-07. Кэш — по измеренной причине
**Уровень:** по умолчанию.
Кэш появляется, когда измерено, что без него не справляемся. У кэша есть
владелец инвалидации, TTL и поведение при недоступности кэша. Права доступа
и деньги не кэшируются без инвалидации.
**Проверка:** вручную.

### PERF-08. Массовые операции — пачками
**Уровень:** обязательно.
Обход больших таблиц — keyset-пачками, запись — batch (`executemany`,
`insert().values([...])`), не по строке и не всё в память.
**Проверка:** вручную — `fetch` без `LIMIT` по большой таблице, вставка в цикле.

## REL — надёжность

Подробности — `reliability.md`.

### REL-01. Бюджет времени запроса
**Уровень:** по умолчанию.
У запроса есть общий дедлайн; таймаут каждого внешнего вызова меньше
оставшегося бюджета. Сумма таймаутов последовательных вызовов не превышает
таймаут клиента/балансировщика.
**Проверка:** вручную.

### REL-02. Повторы — осторожно
**Уровень:** обязательно.
Повторять только идемпотентные операции (или с ключом идемпотентности) и
только временные ошибки: сеть, таймаут, `429`, `502/503/504`. Не повторять
`4xx`. Экспоненциальная задержка с полным джиттером
(`random(0, min(cap, base·2ⁿ))`), потолок попыток, уважение `Retry-After`.
Повторять на одном уровне стека, а не на каждом.
**Почему:** повторы на трёх уровнях по 3 раза — 27 запросов на один; синхронные
повторы всех клиентов добивают упавший сервис.
**Проверка:** вручную — циклы повторов без задержки/потолка, `tenacity` без `stop`.

### REL-03. Отказ зависимости — деградация, а не падение
**Уровень:** по умолчанию.
Необязательная зависимость (рекомендации, аналитика, уведомление) при
отказе не ломает основной путь: фолбэк или пропуск с логом. Обязательная —
быстрый `503`. Для часто падающей зависимости — размыкатель (circuit breaker).
**Проверка:** вручную.

### REL-04. Health: живость отдельно от готовности
**Уровень:** обязательно.
- **liveness** (`/health/live`) — процесс жив и event loop отвечает; зависимости
  **не** проверяет: перезапуск не починит базу, а одновременный перезапуск
  всех экземпляров превратит минутный сбой в долгий.
- **readiness** (`/health/ready`) — реальный запрос в БД и критичные
  зависимости с коротким таймаутом; `503` при сбое.
Без оркестратора (один `/health` для watchdog) — он проверяет БД, как readiness.
Безусловное `ok` запрещено.
**Проверка:** вручную.

### REL-05. Мягкая остановка
**Уровень:** обязательно.
По SIGTERM: перестать принимать новые запросы → дождаться текущих
(таймаут меньше grace period оркестратора, например 25 из 30 с) →
остановить фоновые циклы и потребителей → закрыть клиенты и пулы
(`lifespan`, код после `yield`).
**Проверка:** вручную — `lifespan` закрывает созданное; таймаут остановки задан.

### REL-06. Фоновые циклы
**Уровень:** обязательно.
Тело итерации — в `try/except` с логом: сбой одной итерации не убивает
цикл. Если экземпляров несколько — одна задача выполняется одним
(`pg_try_advisory_xact_lock`, `FOR UPDATE SKIP LOCKED`). Интервал — с
джиттером. Цикл останавливается при остановке процесса (REL-05).
**Проверка:** авто — `while True` в async-функции без `try` в теле.

## OBS — наблюдаемость

Подробности — `observability.md`.

### OBS-01. Структурированные логи
**Уровень:** обязательно.
Одно событие — одна запись с полями (JSON в проде), а не склейка строк.
Уровни: `ERROR` — нужен человек; `WARNING` — деградация, само пройдёт;
`INFO` — бизнес-события и границы процессов; `DEBUG` в проде выключен.
`print` в коде сервиса запрещён.
**Проверка:** авто — `print(` в коде сервиса; ruff `G` (f-строки в логах).

### OBS-02. Корреляция
**Уровень:** обязательно.
`request_id`/`trace_id` — в каждой записи лога (contextvars), передаётся во
внешние вызовы (заголовок), в сообщения брокера и фоновые задачи,
возвращается клиенту в заголовке и в теле ошибки (API-02).
**Проверка:** вручную.

### OBS-03. Что не логировать
**Уровень:** обязательно.
Пароли, токены, ключи, cookie и `Authorization`, платёжные данные,
персональные данные сверх необходимого; полные тела запросов и ответов.
Событие входа логируется — без учётных данных. Токен, если нужен для
расследования, — только хеш.
**Проверка:** авто — вызов логгера с переменной/полем `password`, `token`,
`secret`, `authorization`, `cookie` (эвристика).

### OBS-04. Исключения — один раз, на границе
**Уровень:** обязательно.
Не глотать (`except Exception: pass` запрещён). Логировать со стеком
(`logger.exception`) один раз — там, где исключение обработано (граница
запроса, итерация фонового цикла), а не «залогировал и пробросил» на
каждом уровне.
**Проверка:** авто — `except`/`except Exception` с телом `pass`/`...`; ruff `BLE`.

### OBS-05. Метрики
**Уровень:** по умолчанию.
RED по каждому эндпоинту/обработчику и по каждой внешней зависимости:
частота, ошибки, распределение длительности. Насыщение: занятость пула БД,
длина очередей, отставание дожима. Метки — низкой кардинальности (шаблон
пути, а не URL с id).
**Проверка:** вручную.

### OBS-06. Алерты по симптомам
**Уровень:** по умолчанию.
Алерт — на то, что видит пользователь или деньги: доля ошибок, латентность,
расхождение/отставание дольше порога, а не на CPU. У каждого алерта есть
действие; порог с длительностью, повтор не чаще N.
**Проверка:** вручную.

### OBS-07. Трассировка
**Уровень:** по умолчанию.
OpenTelemetry, когда процессов или сервисов больше одного: спан на запрос,
на внешний вызов и на запрос к БД; `trace_id` — в логах (OBS-02).
**Проверка:** вручную.

## OPS — данные и эксплуатация

Подробности — `operations.md`.

### OPS-01. Время — с часовым поясом, хранится в UTC
**Уровень:** обязательно.
`datetime.now(UTC)`, не `datetime.now()`/`utcnow()`; в БД — `timestamptz`;
между сервисами — UTC. Локальная зона — только при показе человеку и в
правилах, где она по смыслу («до конца дня по Москве»), явно.
**Проверка:** авто — `datetime.now()` без зоны, `utcnow()`, `date.today()`; ruff `DTZ`.

### OPS-02. Деньги — не `float`
**Уровень:** обязательно.
`Decimal` или целое в минорных единицах (копейки) плюс валюта. Округление —
явно, в домене, одним правилом. В БД — `numeric`/`bigint`.
**Проверка:** авто — аннотация `float` у полей `price`, `amount`, `sum`, `cost`,
`balance`, `total`, `fee` (эвристика).

### OPS-03. Настройки проверяются при старте
**Уровень:** обязательно.
pydantic-settings: нет обязательной настройки или она неверна — процесс не
стартует, с понятной ошибкой. У секретов нет значений по умолчанию. Настройки
разделены по назначению; сценарий получает свой `Config` (DEP-03).
**Проверка:** вручную — `os.getenv` в коде, значения по умолчанию у секретов.

### OPS-04. Миграции без простоя
**Уровень:** обязательно.
- expand → migrate → contract: сначала совместимое расширение схемы, затем
  код, затем удаление старого — отдельным релизом.
- Переименование колонки/таблицы — через новую и двойную запись, не `RENAME`.
- `SET lock_timeout` в начале миграции (секунды), при неудаче — повтор, а
  не ожидание в очереди блокировок.
- Индекс на живой таблице — `CREATE INDEX CONCURRENTLY` (вне транзакции).
- `NOT NULL` на большой таблице — `CHECK (...) NOT VALID` → `VALIDATE` → `SET NOT NULL`.
- Бэкфилл — пачками, вне миграции схемы.
**Почему:** одна миграция с долгой блокировкой останавливает все запросы к таблице.
**Проверка:** авто (в `migrations/`) — `create_index` без `postgresql_concurrently`,
`add_column(... nullable=False)` без `server_default`, `alter_column(... nullable=False)`,
`rename`, нет `lock_timeout` (предупреждения).

### OPS-05. Выкатка совместима в обе стороны
**Уровень:** обязательно.
Миграции применяются до запуска новой версии; новая версия работает со
старой схемой на время выкатки, старая — с новой. Откат кода не требует
отката схемы.
**Проверка:** вручную.

### OPS-06. Рискованное включается отдельно от выкатки
**Уровень:** по умолчанию.
Новый платёжный путь, массовая рассылка, смена правила денег — за флагом или
настройкой, с обкаткой на части пользователей (тестовые id) перед всеми.
**Проверка:** вручную.

### TST-02. Адаптеры — на настоящей тестовой БД
**Уровень:** обязательно.
Не моки сессии. Проверить, что без коммита запись откатывается.

**Уровень:** обязательно.

### TST-05. Контейнер собирается

### TST-06. Изменение поведения — сначала падающий тест

**Проверка:** вручную.

## LEG — перенос старого кода

### LEG-01. Новое — только в новой структуре
**Уровень:** обязательно.
В старые большие модули новую логику не добавлять; они только уменьшаются.
**Проверка:** авто — рост строк в модулях из контракта legacy (diff).

### LEG-02. Сначала тесты на текущее поведение
**Уровень:** обязательно.
Тесты пишутся против старого кода, отдельным коммитом без изменений в
`src/`. После переноса — те же тесты, без изменений, зелёные. Для операций
над многими таблицами — тест-снимок.
**Проверка:** вручную — история коммитов.

### LEG-03. Перенос не меняет поведение
**Уровень:** обязательно.
Тексты, сроки, цены, порядок шагов — прежние. Найденный баг — отдельным
изменением до или после переноса, не внутри.
**Проверка:** вручную.

### LEG-04. Мост к старому коду — порт
**Уровень:** обязательно.
Нужно правило/данные из неперенесённого кода — порт в
`application/interfaces/`, адаптер `adapters/legacy_<что>.py`. При переносе
меняется только адаптер.
**Проверка:** авто — импорт старых модулей вне `adapters/legacy_*`.

### LEG-05. Старый код вызывает новый — через обёртку
**Уровень:** по умолчанию.
Метод старого модуля становится однострочной обёрткой над функцией
домена. Логика в одном месте.
**Проверка:** вручную.

### LEG-06. Поэтапно и коротко
**Уровень:** обязательно.
Домен перенесён → слияние в основную ветку → выкатка. Долгоживущая ветка
переноса запрещена. Порядок — от листьев графа зависимостей к центру.
**Проверка:** вручную.
