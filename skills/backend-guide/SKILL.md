# Руководство по бэкенду

Все правила — в `catalog.md` (номера `STR-01`, `TX-02`…). Этот файл говорит,
что читать и в каком порядке. Не пиши код, пока не прочитал нужные файлы.

## 1. Сначала — правила проекта

1. Прочитать `AGENTS.md` / `CLAUDE.md` проекта, раздел «Отклонения от общих
   правил». Записанное там важнее этого руководства.
2. Найти в проекте домен-образец (самый аккуратный уже перенесённый домен)
   и делать так же, как в нём, если это не противоречит обязательным правилам.

## 2. Что читать под задачу

| Задача | Читать |
|---|---|
| Новый проект | `new-project.md`, затем `domain-template.md` |
| Новый домен | `domain-template.md` |
| Новый сценарий, порт, адаптер | `domain-template.md` (разделы слоя), `catalog.md` APP, TX |
| Запись в несколько доменов, события, вебхуки | `transactions.md` |
| Перенос старого кода | `legacy-migration.md` |
| Не знаю, куда положить код | таблица «Куда класть» ниже |
| Эндпоинт, схемы, ошибки, пагинация, идемпотентность | `api.md` |
| Доступ к объектам, роли, вебхуки, секреты, исходящие запросы по URL | `security.md` |
| Медленный запрос, индексы, пул, массовые операции, очередь, кэш | `performance.md` |
| Вызов внешнего API, повторы, health, остановка, фоновый цикл | `reliability.md` |
| Логи, метрики, алерты, трассировка | `observability.md` |
| Время, деньги, настройки, миграции на живой БД, выкатка | `operations.md` |
| Стек: SQLAlchemy / asyncpg / aiogram / FastStream | `stacks/<имя>.md` |

Правило по номеру — `catalog.md`, поиск по `### <номер>`.

## 3. Куда класть

| Что | Куда |
|---|---|
| Условие про деньги, сроки, доступ, статус | `domain/` — чистая функция (DOM-01) |
| Ответ «нельзя, потому что…» | `domain/` — функция возвращает причину (DOM-02) |
| Последовательность шагов одного агрегата | `application/interactor.py` |
| Одна транзакция пишет несколько доменов | `application/<сценарий>.py` — Service (APP-04) |
| Чтение для ответа пользователю | View, вызывает контроллер (APP-03) |
| Чтение, по которому сценарий решает | метод Gateway (APP-03) |
| SQL, ORM | `adapters/` (DB-01) |
| Клиент внешнего API | клиент — `infrastructure/<сервис>/`, порт — `application/interfaces/`, адаптер — `adapters/` (APP-06) |
| Настройка, которая нужна сценарию | `application/config.py` → `{Что}Config`, собирает провайдер (DEP-03) |
| Тексты, кнопки, схемы запроса/ответа | `controllers/` (CTL-02) |
| То, что нужно соседу | `public.py` (DEP-04) |
| Общая техника (пул, http, почта) | `infrastructure/<назначение>/` (STR-04) |
| Реакция на событие другого домена | `controllers/` обработчик → сценарий своего домена |
| Фоновая периодическая задача | точка сборки запускает, тело — сценарий домена |

## 4. Порядок работы над фичей

1. Определить домен-владелец каждой таблицы и правила, которых касается фича.
2. Правило — в `domain/` с модульными тестами (сначала тест).
3. Порт(ы) в `application/interfaces/`, сценарий, `Info`.
4. Адаптеры + тесты на тестовой БД (с проверкой отката).
5. `ioc.py`, `public.py` (если нужно соседям), контроллер: схемы, ошибки,
   доступ, пагинация (`api.md`, чек-лист в `security.md`).
6. Контракты import-linter для нового домена; модуль — в mypy strict.
7. `backend-review` по изменениям.

## 5. Нельзя без согласования

Нарушать правило уровня «обязательно». Если без этого никак — объяснить
пользователю, почему, предложить запись в «Отклонения» и ждать решения.
