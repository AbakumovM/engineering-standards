# Ревью фронтенда

Проверяешь код по каталогу `../frontend-guide/catalog.md`. Ничего не
исправляешь, пока пользователь не попросит: результат — отчёт.

## 0. Режим

- Аргумент `repo` → **весь репозиторий**.
- Иначе → **изменения ветки** относительно базы: аргумент, или `develop`/`main`
  (`git merge-base HEAD <ветка>`), плюс незакоммиченное.

Монорепозиторий: фронтенд — каталог с `package.json` (`web/`, `frontend/`);
все команды — из него.

## 1. Правила проекта

1. Прочитай `AGENTS.md` / `CLAUDE.md` / `GIGACODE.md` проекта. Выпиши раздел
   «Отклонения от общих правил»: эти отступления — **не** нарушения.
2. Найди старый код (раздел о переносе в инструкциях проекта) — передать
   скрипту в `--legacy`.
3. Посмотри `package.json`: стек проекта может отличаться от стека по
   умолчанию. Отличие без записи в «Отклонениях» — вопрос в отчёт, а не
   ошибка в каждой строке.

## 2. Механические проверки

```bash
python3 <путь к скиллу>/scripts/fe_check.py [--diff <база>] [--legacy src/legacy]
pnpm lint          # или npm run lint — по lock-файлу проекта
pnpm typecheck     # или tsc --noEmit
pnpm test
pnpm knip          # если настроен
```

Нет скрипта в `package.json` — скажи об этом в отчёте, не придумывай команду.
Каждую находку скрипта **проверь глазами**: открой строку, убедись, что это
нарушение. Ложное — не включай, но упомяни в конце («скрипт ошибся в …»).

## 3. Проверки по смыслу

Номер — правило каталога; перед выводом перечитай его там.

**Структура и границы**
- [ ] FSTR-01, FSTR-03: код в `features/`/`shared/`, нет свалок по типу.
- [ ] FDEP-01…FDEP-04: импорт вниз; чужая фича — через `index.ts`; компоновка в маршруте.
- [ ] FSTR-05: файл маршрута — параметры, загрузка, компоновка; нет бизнес-условий.

**Компоненты и состояние**
- [ ] FCMP-01: условия «можно ли», статусы, суммы — в `model/`, не в JSX.
- [ ] FCMP-02, FCMP-03: нет загрузки в `useEffect`; эффект — только синхронизация; производное — при рендере.
- [ ] FSTATE-01: ответ сервера не скопирован в `useState`/стор.
- [ ] FSTATE-02: фильтры, страница, вкладка — в URL со схемой.
- [ ] FSTATE-05: нет двух источников одного значения.

**API**
- [ ] FAPI-01, FAPI-02: типы и вызовы — из сгенерированного клиента; нет ручных типов ответов и `fetch`.
- [ ] FAPI-03: после мутации — инвалидация/`setQueryData` нужных ключей.
- [ ] FAPI-04: ошибки — через общий разбор; `422` — у полей; `401` — один обработчик.
- [ ] FAPI-05: список — курсор, нет «загрузить всё».
- [ ] FAPI-06, FFORM-04: создание/оплата — `Idempotency-Key`, кнопка заблокирована на время запроса.
- [ ] FAPI-07: мутации не повторяются автоматически; `4xx` не повторяются.

**Формы и маршруты**
- [ ] FFORM-01…FFORM-03: схема Zod, `zodResolver`, серверные ошибки у полей.
- [ ] FRTE-01: `validateSearch` со схемой; неверный параметр не роняет страницу.
- [ ] FRTE-02: данные страницы — `loader`, нет каскада «смонтировался → запрос → ещё запрос».
- [ ] FRTE-05: `errorComponent`/`notFoundComponent` у корня.

**Безопасность** (подробно — `../frontend-guide/security.md`)
- [ ] FSEC-01: HTML из данных — только через DOMPurify.
- [ ] FSEC-02: токенов нет в `localStorage`/`sessionStorage`/URL.
- [ ] FSEC-03: при cookie-сессии — CSRF-заголовок на изменяющих запросах.
- [ ] FSEC-04: нет секретов в `VITE_*` и в коде.
- [ ] FSEC-06: ссылки и редиректы из данных проверены (`safeHref`, `safeNext`).
- [ ] FSEC-07: действие, скрытое от роли, бэкенд тоже запрещает (если бэкенд в том же репозитории — проверить).
- [ ] FSEC-08: новые зависимости — нужны, поддерживаются, lock-файл обновлён.
- [ ] FSEC-09, FSEC-10: `postMessage` с проверкой `origin`; нет `eval`.
- [ ] FSEC-11: персональные данные не в URL, хранилище, сборе ошибок; выход очищает кэш.

**Скорость и доступность**
- [ ] FRTE-04, FPERF-06: маршруты в отдельных чанках; нет тяжёлых библиотек без нужды.
- [ ] FPERF-04: длинный список — виртуализация или пагинация.
- [ ] FA11Y-01…FA11Y-03: семантичные элементы, клавиатура, подписи.
- [ ] FA11Y-05: модалки и меню — примитивы shadcn/ui, не самописные.

**Ошибки и тесты**
- [ ] FOBS-01, FOBS-03: Error Boundary есть; ошибки не глотаются.
- [ ] FOBS-02, FOBS-05: сбор ошибок с релизом; `request_id` на экране ошибки.
- [ ] FTST-01: у функций `model/` — тесты.
- [ ] FTST-02, FTST-03: компоненты — по ролям, сеть — MSW, есть сценарий ошибки.
- [ ] FTST-04: главный путь фичи покрыт e2e (если в проекте есть e2e).
- [ ] FTS-02…FTS-04: нет `any`, подавления с причиной, внешние данные через схему.

### Прежде чем назвать нарушением

Найди 2–3 похожих места в проекте. Если везде так же — это, вероятно,
принятое в проекте решение: вынеси в «Вопросы о правилах» (записать
отклонение или исправить везде), а не в ошибки каждой строки.

Порядок: безопасность → данные и API → границы → остальное. Каждая находка —
номер, файл:строка, что не так, почему плохо, как исправить (одной фразой).
Без находок раздел не выводить. В режиме `repo` в начале — 3–5 главных
проблем, которые стоит исправить первыми.
