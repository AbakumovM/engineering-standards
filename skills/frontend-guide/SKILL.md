# Руководство по фронтенду

Все правила — в `catalog.md` (номера `FSTR-01`, `FAPI-04`…). Этот файл
говорит, что читать и в каком порядке. Не пиши код, пока не прочитал нужное.

## 1. Сначала — правила проекта

1. Прочитать `AGENTS.md` / `CLAUDE.md` проекта, раздел «Отклонения от общих
   правил». Записанное там важнее этого руководства.
2. Найти в проекте фичу-образец (самую аккуратную) и делать так же, если это
   не противоречит обязательным правилам.
3. Версии библиотек — из `package.json` проекта. API библиотеки, в котором
   не уверен, — сверить с документацией этой версии (context7, сайт
   библиотеки), а не писать по памяти.

## 2. Что читать под задачу

| Задача | Читать |
|---|---|
| Новый проект | `new-project.md`, затем `feature-template.md` |
| Новая фича, маршрут | `feature-template.md` |
| Запрос, мутация, ошибки API, пагинация, повторная отправка | `api.md` |
| Где хранить состояние; форма | `state-and-forms.md` |
| Вход, токены, HTML из данных, ссылки, CSP, новая зависимость | `security.md` |
| Медленно, большой бандл, длинный список, доступность | `performance-a11y.md` |
| Тесты, моки сети, e2e, сбор ошибок | `testing.md` |
| Перенос старого кода, смена сборщика/библиотек | `legacy-migration.md` |
| Не знаю, куда положить код | таблица «Куда класть» ниже |

Правило по номеру — `catalog.md`, поиск по `### <номер>`.

## 3. Куда класть

| Что | Куда |
|---|---|
| Условие «можно ли», статус, сумма, формат для показа | `features/<фича>/model/` — чистая функция с тестом (FCMP-01) |
| Запросы и мутации фичи (options, ключи, инвалидация) | `features/<фича>/api/` (FAPI-03) |
| Схема формы | `features/<фича>/model/<форма>-schema.ts` (FFORM-01) |
| Компонент фичи | `features/<фича>/ui/` |
| То, что нужно другим фичам и маршрутам | экспорт из `features/<фича>/index.ts` (FDEP-03) |
| Страница, параметры URL, загрузка данных страницы | `routes/` (FSTR-05, FRTE-01, FRTE-02) |
| Кнопка, поле, таблица, модалка без бизнес-смысла | `shared/ui/` (FDEP-02) |
| Настройка клиента API, разбор ошибок | `shared/api/` (FAPI-02, FAPI-04) |
| Форматирование, работа с датами — без бизнес-смысла | `shared/lib/<назначение>/` (FSTR-03) |
| Переменные окружения | `shared/config/env.ts` — схема Zod (FTS-04) |
| Провайдеры, корневые ошибки, стили | `app/` |
| Общее клиентское состояние нескольких страниц | `features/<фича>/model/<что>-store.ts` (FSTATE-03) |

## 4. Порядок работы над фичей

1. Эндпоинты бэкенда есть в OpenAPI → `pnpm api:generate`. Нет — сначала
   бэкенд или согласовать схему.
2. Правила отображения — в `model/` с тестами (сначала тест).
3. `api/`: options запросов, мутации, инвалидация (`api.md`).
4. `ui/`: компоненты из `shared/ui`; формы — `state-and-forms.md`.
5. Маршрут: `validateSearch`, `loader`, компоновка, `errorComponent`.
6. Тесты компонентов с MSW, включая ошибки; e2e для главного пути (`testing.md`).
7. `pnpm lint && pnpm typecheck && pnpm test && pnpm knip`, затем `frontend-review`.

## 5. Нельзя без согласования

Нарушать правило уровня «обязательно», добавлять зависимость не из стека,
менять сборщик, роутер или менеджер состояния. Если без этого никак —
объяснить пользователю, почему, предложить запись в «Отклонения» и ждать
решения.
