# Ревью бэкенда

Проверяешь код по каталогу правил `../backend-guide/catalog.md`. Ничего
не исправляешь, пока пользователь не попросит: результат — отчёт.

## 0. Режим

- Аргумент `repo` → **весь репозиторий**.
- Иначе → **изменения ветки** относительно базы: аргумент, или `develop`/`main`
  (`git merge-base HEAD <ветка>`), плюс незакоммиченное.

## 1. Правила проекта

1. Прочитай `AGENTS.md` / `CLAUDE.md` / `GIGACODE.md` проекта. Выпиши раздел
   «Отклонения от общих правил»: эти отступления — **не** нарушения.
2. Найди старые модули (контракт `legacy` в `.importlinter`, раздел о переносе
   в инструкциях проекта) — их передать скрипту в `--legacy`.

## 2. Механические проверки

Запусти из корня проекта (Python проекта — чтобы разобрался его синтаксис):

```bash
uv run python <путь к скиллу>/scripts/arch_check.py [--diff <база>] [--legacy app.old app.legacy_storage]
uv run lint-imports        # если есть .importlinter
uv run mypy                # если настроен
uv run ruff check .
```

Если `uv` нет — `python3`. Скрипт сам учитывает `ignore_imports` из
`.importlinter` и подавления `# arch-ignore[ID]: причина`.

Каждую находку скрипта **проверь глазами**: открой строку, убедись, что это
нарушение, а не ложное срабатывание. Ложное — не включай в отчёт, но упомяни
в конце («скрипт ошибся в …»), чтобы правило уточнить.

## 3. Проверки по смыслу

Для каждого изменённого (или, в режиме `repo`, каждого) домена пройди чек-лист.
Номер — правило каталога; перед выводом перечитай правило там.

**Контроллеры** (`controllers/`)
- [ ] CTL-01: нет условий про деньги, сроки, доступ, статусы; не создаёт сущности; не ходит в Gateway.
- [ ] APP-05: оркестрация 1–2 сценариев; больше и переиспользуется — нужен Service (APP-04).
- [ ] TX-02, TX-03: внешние вызовы — до сценария или после коммита; порядок безопасен при сбое.
- [ ] CTL-03: доступ — фильтром/зависимостью.

**Сценарии** (`application/`)
- [ ] APP-01: один Gateway записи; чужие — только порты соседей в сервисе.
- [ ] APP-02: возвращает `Info`/значения, не доменную модель и не строку ORM.
- [ ] APP-03: свой View в конструкторе отсутствует; решение — по данным Gateway.
- [ ] APP-05: нет Interactor соседа в конструкторе.
- [ ] TX-01: каждый путь метода заканчивается `commit()` или `rollback()`/исключением.
- [ ] TX-02: между первым обращением к Gateway и commit нет портов внешних сервисов.
- [ ] TX-04: порт соседа в чужой транзакции не коммитит.
- [ ] TX-09: нет `publish()`; события наружу — outbox.
- [ ] DEP-03: настройки — `{Что}Config`, не `Settings`.

**Домен** (`domain/`)
- [ ] DOM-01: правила, которые фича добавила, лежат здесь, а не в контроллере/SQL.
- [ ] DOM-02: «можно ли» возвращает причину.
- [ ] DOM-04: правило соседа не скопировано.

**Адаптеры** (`adapters/`)
- [ ] DEP-05: SQL не трогает чужие таблицы (сверь с владельцами из инструкций/design проекта).
- [ ] TX-07: перехват конфликта уникальности — внутри savepoint.
- [ ] TX-08: общая блокировка — первым шагом, порядок как в других путях.
- [ ] ADP-02: ошибки внешнего API → одно исключение порта.
- [ ] ADP-04: нет выборки всего с фильтром в Python, нет N+1.

**Сборка и границы**
- [ ] DEP-04: новое, что нужно соседям, — в `public.py`.
- [ ] DEP-06: для нового домена есть контракты import-linter; новые `ignore_imports` — с «когда снимется».
- [ ] DI-01, DI-03: провайдеры по слоям, области жизни верные.
- [ ] TYP-01: новые модули в mypy strict.

**Вебхуки и обработчики событий** — если фича их трогает
- [ ] TX-10: проверка «уже исполнено»; неидемпотентный шаг и отметка — в одной транзакции; есть дожим.

**HTTP API** — если фича добавила или изменила эндпоинт
- [ ] API-01: явные схемы; ответ из `Info`; `extra="forbid"`; нет полей, которые клиент менять не вправе.
- [ ] API-02, API-03: ошибки — общим обработчиком, единым форматом, коды по смыслу.
- [ ] API-04: список — `limit` с потолком и курсор; сортировка с уникальным хвостом.
- [ ] API-05: создающий/платёжный `POST` — ключ идемпотентности.
- [ ] API-06: изменение схемы ответа/запроса совместимо (сравни с основной веткой).
- [ ] API-07: потолки длин, размеров, диапазонов.

**Безопасность** — пройти чек-лист из `../backend-guide/security.md`
- [ ] SEC-01: каждый путь «по id» фильтрует по субъекту/арендатору; чужое — 404.
- [ ] SEC-02: новый админский/служебный маршрут — под роутером с ролью.
- [ ] SEC-04, OBS-03: секреты и персональные данные не попадают в код, ответы, логи.
- [ ] SEC-06, SEC-07, SEC-08: вебхуки с подписью; исходящие запросы по URL из ввода — защищены; чужие ответы разбираются схемой.
- [ ] SEC-09: дорогие и чувствительные операции (вход, коды, письма, оплата) — с лимитом частоты.

**Нагрузка и надёжность**
- [ ] PERF-01, PERF-02: нет запросов в цикле; под новый запрос есть индекс (проверь миграции).
- [ ] PERF-05, PERF-06: параллельность ограничена; долгая работа — не в запросе.
- [ ] PERF-08: массовые операции пачками.
- [ ] REL-01, REL-02: у новых внешних вызовов таймаут; повторы — только идемпотентного, с джиттером, на одном уровне.
- [ ] REL-03: падение необязательной зависимости не ломает основной путь.
- [ ] REL-05, REL-06: новый фоновый цикл переживает сбой итерации, останавливается с процессом, не дублируется на нескольких экземплярах.

**Логи и данные**
- [ ] OBS-01, OBS-04: события — структурированные, исключения не глотаются, логируются один раз.
- [ ] OPS-01, OPS-02: время с зоной, деньги не `float`, округление в домене.
- [ ] OPS-04, OPS-05: миграция совместима со старой версией кода, `lock_timeout`, индексы `CONCURRENTLY`, нет `RENAME`/`DROP` того, что читает текущий код.

**Тесты**
- [ ] TST-01: новые правила домена покрыты модульными тестами.
- [ ] TST-02: новые методы адаптеров — тест на тестовой БД.
- [ ] TST-03: новый сценарий — тест через точку входа.
- [ ] LEG-02, LEG-03: если это перенос — тесты на старое поведение были раньше и не менялись.

## 4. Прежде чем назвать нарушением

1. Найди в проекте 2–3 места, где то же сделано (поиск по имени/паттерну).
2. Если везде одинаково и это записано в «Отклонениях» — не нарушение.
3. Если везде одинаково, но не записано — это **находка про правила**, а не
   про код: предложи записать отклонение или исправить везде.
4. Если правило каталога этого случая явно не покрывает — не выдумывай: опиши
   как вопрос.

- Каждая находка: номер правила, `файл:строка`, что не так, почему это важно
  (одна фраза из «Почему» каталога), как исправить.
- Сначала ошибки, затем предупреждения; внутри — по серьёзности последствий.
- Нарушений нет — так и написать, перечислив, что проверено.
- Режим `repo` — в конце сводка по доменам (таблица: домен × число находок)
  и список правил «вручную», для которых стоит добавить автопроверку.
